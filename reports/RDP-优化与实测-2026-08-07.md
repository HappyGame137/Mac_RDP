# Mac ↔ Windows RDP 优化与实测记录（2026-08-07）

## 结论

RDP 的主机硬编、客户端硬解、4K 清晰度和 60 FPS 上限均已打通。用户最终 A/B 结论是：Mac Low Latency RDP 的界面动画略优于 Windows App，但 4K 视频明显更卡；因此 4K 连续画面的主要差距已收敛到 FreeRDP/SDL 客户端帧管线，而非 Windows 编码器。Wi‑Fi 周期性尖峰仍会叠加卡顿，但不能单独解释两个客户端在同一网络上的差异。

建议保留三条路线：Mac Low Latency RDP 用于交互动画、文字办公、管理和外网；Windows App 用于当前环境中的 4K 视频；Moonlight 用于游戏和高帧率动态画面。

## 操作边界

- Windows 端全程只通过既有 RDP 会话操作。
- 未开启 SSH、WinRM、OpenSSH Server 或其他持久远控通道。
- Windows 写入型优化均先保存原值并生成恢复脚本。
- 不公开暴露 TCP/UDP 3389；外网建议使用受控 VPN 或 RD Gateway。

## FreeRDP 图形与传输 A/B

客户端为 FreeRDP 3.30.0，构建已确认 `WITH_GFX_H264=ON`、`WITH_FFMPEG=ON`、`WITH_VIDEOTOOLBOX=ON`；渲染器为 Metal，H.264 解码使用 VideoToolbox。

| 组合 | 远端分辨率 | 请求 | 实际图形路径 | 静态 RSS | 实际传输 |
|---|---:|---|---|---:|---|
| 4K 视频旧实验 | 4096×1716 | AVC420 + video | ClearCodec/Progressive；未选中视频通道 | 约 606 MB | TCP |
| 4K 最低排队 | 4096×1716 | AVC420、ACK 1 | ClearCodec | 约 611 MB | TCP |
| 均衡 | 3072×1288 | AVC420、ACK 2 | ClearCodec | 约 394 MB | TCP |
| 清晰/新视频默认 | 4096×1716 | AVC444、ACK 2/4 | **AVC444v2** | 约 636 MB | TCP |

高动态 AVC444v2 会话中客户端 CPU 约 14–20%，持续收到 AVC444v2 surface 命令。`+async-update` 的日志明确显示被 SDL 前端强制关闭，因此客户端已将其固定为关闭并在界面标明。

结论：需要当前文字大小和清晰度时使用 4K AVC444v2；弱网或需要降低内存/带宽时用 3072×1288 均衡预设。原“AVC420 + video”没有在桌面视频测试中协商到预期通道，已从界面移除。4K 视频改用 Windows App；保留的“视频兼容（3K）”只是降低表面尺寸和排队，并不宣称能达到 Windows App 的 4K 表现。

### FreeRDP UDP 实现核对

FreeRDP 3.30.0 客户端源码的 Multitransport 回调会以 `E_ABORT` 拒绝 UDP 初始化。因此“Windows 主机 UDP 3389 已监听”“命令带 `+multitransport`”和“客户端实际使用 UDP”是三件不同的事；此前所有会话只有 TCP 也与源码行为一致。v0.9 固定传入 `-multitransport`，移除无效的“尝试 UDP”开关，等待上游真正实现后再恢复。

## RemoteApp/只连接应用

实验命令 `quality remoteapp '||notepad'` 已完成 RAIL 虚拟通道加载、`TS_RAIL_ORDER_HANDSHAKE_EX` 握手，并收到多个 `map_surface_to_scaled_window` 窗口映射；图形路径为 AVC444v2，但用户目视结果为黑屏。`/shell` 应用启动兼容模式也黑屏并退出。

结论是“协议握手成功”不等于“功能可用”。Windows Pro 不是微软正式支持的 RemoteApp 发布主机，且当前 SDL3 窗口呈现结果不可用。v0.9 已将 RemoteApp 和 `/shell` 应用启动从界面停用；底层参数生成与测试保留，未来仅在 Windows Server RDS、Azure Virtual Desktop 或 Windows 365 上重新验证。

### v0.9.1 预设与实际协议显示修正

用户反馈在已连接的 4K 清晰会话中点击“低延迟动画”后，紫色状态仍显示 AVC444v2。日志复核确认这不是两个预设协商结果相同，而是 FreeRDP 的图形能力不能在现有会话中热切换：08:22 的 4K 清晰连接为 `/gfx:AVC444` → `AVC444v2`，点击预设只修改下一次连接参数，当前进程仍保持 AVC444v2；08:21 的 `/gfx:AVC420` 连接实际 surface codec 为 `ClearCodec + Progressive`，日志中没有 AVC444。

v0.9.1 在连接期间禁用预设按钮和高级连接参数，明确提示“断开后选择、重新连接生效”；紫色标签改为“实际：…”，并新增“下次连接”参数摘要。协议分析器不再把 VideoToolbox/H.264 解码器初始化误当成实际 surface codec，只根据 `RDPGFX_CODECID_*` 命令报告 AVC444v2、AVC420、ClearCodec 或 Progressive。

### v0.9.2 合并无有效差异的 4K 预设

用户随后在断开重连后直接比较两个 4K 模式，主观体验仍看不出区别。日志确认两者协议不同，但总体客户端负担几乎相同：

| 模式 | 实际 surface codec | PERF 样本 | 平均 CPU | 峰值 CPU | 平均 RSS | 峰值 RSS |
|---|---|---:|---:|---:|---:|---:|
| 旧低延迟动画 | ClearCodec + Progressive | 16 | 26.4% | 106.6% | 613 MB | 703 MB |
| 旧 4K 清晰文字 | AVC444v2 | 14 | 26.8% | 70.0% | 595 MB | 674 MB |

这两次会话较短，且不能证明负载逐帧完全一致，因此数字只作为方向性证据；但“用户目视无区别 + 平均 CPU/RSS 基本相同”足以否定把它们包装为两个有效体验预设。v0.9.2 将两者合并为“4K 日常（推荐）”，采用 AVC444v2 保留文字/色彩能力；另一项只保留真正改变像素负担的“3K 流畅 / 外网”，其远端像素数量比 4K 预设少约 44%。旧低延迟和视频模式仍保留在配置兼容及测试代码中，但不再显示按钮。

## 仍存在的深层限制

FreeRDP 的 VideoToolbox 路径仍会把硬件帧转回 CPU/BGRA，再交给 SDL/Metal 上传；真正的 `CVPixelBuffer/IOSurface → Metal` 零拷贝需要修改 FreeRDP codec、RDPGFX surface 与 SDL renderer，不能靠注册表或单个参数实现。有线网络 A/B 仍有助于隔离 Wi‑Fi 尖峰，但不会消除已实测的 FreeRDP 与 Windows App 之间的 4K 视频差距；是否维护专用 FreeRDP fork应等待上游进展。
